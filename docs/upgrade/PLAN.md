# Upgrade plan: audit and phases

Status: **draft, waiting for approval** (2026-10-05). Nothing in the codebase has
been changed yet.

This plan covers the 18-module brief. The first part describes what exists today.
The second part shows how each module fits into the existing design. The third
part lists the phases. The decisions that need the owner are at the end.

---

## 1. What exists today

| | |
| --- | --- |
| Stack | npm workspaces monorepo. `apps/api` is NestJS 11 + Drizzle ORM. `apps/web` is Next.js 15 (App Router, server components) + Tailwind v4. `packages/shared` holds the domain rules and the Zod schemas, and both apps import it. |
| Database | Postgres. In development it is embedded PGlite in `.data/pg`, single-writer and guarded by a lock. In production `DATABASE_URL` points it at a real Postgres. 22 tables. 6 migrations, generated by drizzle-kit, with backfills written by hand (`0001`). |
| Size | About 35,700 lines of TypeScript: API 13.7k, web 19.6k, shared 2.4k, tests 2.0k. 114 endpoints and 58 pages. |
| Tenancy | Every tenant row has a `tenant_id`. The tenant is resolved from the signed-in user's own row on every request, never from the host. Each service has its own `scope()`. `tenantOf()` throws rather than return null. Storage keys are prefixed `tenants/<id>/`. A cross-tenant attack suite covers this. |
| Auth / RBAC | There are 4 roles in a pg enum: `client`, `consultant`, `manager`, `super_admin`. Each role has one portal: `/portal`, `/desk`, `/overview`, `/admin`. There are 23 permissions with three layers: member override, then the consultancy default, then the built-in default. A global `AuthGuard` checks `@Public`, `@Roles`, `@RequiresModule` and `@RequirePermission`. The user is re-read on every request in one query. Managers always hold every permission. |
| Security | Two-step sign-in with TOTP. Secrets are encrypted with AES-256-GCM and recovery codes are hashed. A tenant MFA policy exists. Sign-in is throttled and each account has a token-bucket rate limit. File uploads are checked by their leading bytes. CSV exports are made formula-safe and audited. |
| Audit | `audit_log` is append-only and enforced by a database trigger. Each row stores the IP, the user agent and metadata with before/after values. Staff views are recorded with 15-minute de-duplication. |
| Background work | Two timers run inside the API process: the stuck-case sweep (daily) and the overdue-task sweep (every 15 minutes). There is no queue, no email and no SMS or WhatsApp. |
| Realtime | Socket.IO for case chat and notifications, with one room per user. |
| Plans | Plans are platform-level and switch three modules on or off (`billing`, `tasks`, `announcements`). They also set limits on staff, active clients and storage. |
| UI | A token design system (`globals.css`) with dark mode, Rubik, a navy rail and shared primitives in `components/ui.tsx` and `forms.tsx`. Charts are custom SVG with accessible tables. The layout is mobile-first. |
| Tests | `node:test` integration suites boot the real API on a throwaway database. **Baseline today: 64/64 passing (44 s).** There are no unit tests for the web app and no E2E tests. An API benchmark and a page benchmark count every SQL query. |
| Missing infra | **The project is not a git repository.** Git is installed. There is no CI, no Docker (not installed on this machine), no linting, no i18n and no error tracking. |

Conventions that the new work keeps:

- Domain rules live in `@crm/shared`, so the browser and the server always agree.
- Each resource has one `scope()` in SQL. A record the caller may not see returns `404`.
- Lists use the text-plus-validation pattern rather than pg enums wherever values will grow. New permission keys and audit actions need no migration.
- Money is stored in minor units and totalled per currency. Ledgers are append-only, and corrections are made with void or reversal entries.
- Every external service sits behind a seam: the auth provider, the storage driver, and next the mailer, messaging, payment gateway and AI.
- Query count is the performance metric. The page benchmark must not regress without an explanation.

## 3. How the new modules fit the existing model

These are the structural choices that shape everything after them.

### 3.1 Roles: keep the 4 portals, add role templates and 2 portal roles

Today a role decides the portal and permissions decide the capabilities. The plan
keeps that split rather than adding a pg enum value for every job title:

| Brief's role | Implemented as |
| --- | --- |
| Super Admin | `super_admin` (unchanged) |
| Agency Admin | `manager`: the owner, who always has everything (unchanged) |
| Manager (branch), Consultant, Accountant, Trainer | `consultant` portal role (`/desk`) + a **role template**. A role template is a tenant-editable named permission set with a data scope of *own / branch / all*. Four templates are seeded. A tenant can add more, such as "Visa officer". |
| Partner / Sub-agent | **New** `partner` role with its own `/partner` portal. It sees only its own students. |
| Student / Client | `client` (unchanged) |
| Parent / Guardian (M11) | **New** `guardian` role. It has read-only access to one client, with consent. |

Permission resolution becomes: member override → role template → consultancy
default → built-in default. The resolution still happens inside the single query
that loads the user. The permission catalogue grows per module and is still text
keys, so no migration is needed. `client.view_all` maps onto data scope `all`.
Adding the two enum values (`ALTER TYPE ... ADD VALUE`) is additive. The DB value
`consultant` is kept rather than renamed. The UI labels each person by their
template, such as "Accountant".

### 3.2 Stages: from a fixed enum to versioned workflow templates

This is the riskiest change in the program. `STAGE_DEFINITIONS` currently drives
auto-advance, transitions, checklists, the stuck sweep, every funnel and dashboard
query, and the client's progress bar.

- New tables: `workflow_templates` (per country and optionally per level or visa
  type), `workflow_versions` (immutable once published), and `workflow_stages`
  (key, labels, colour, order, SLA days, required-document set, auto-tasks, fees,
  message templates, approval gate, who may move, conditions).
- `cases` gains `workflow_version_id` and `current_stage_key`, and
  `case_stage_events` gains `stage_key`. Each tenant gets a **"Standard" template
  that reproduces today's 10 stages exactly**, and every existing case is
  attached to it.
- A published version never changes under a running case. Editing creates a new
  version, and a case moves to it only when someone chooses to.
- The old `current_stage` enum column stays populated for Standard-template cases
  during the transition. It is dropped later, and only with your approval.
- Verification works the way it did in the second performance pass. API responses
  are snapshotted before and after on identical copies of the database. For
  Standard-template cases they must not differ.

### 3.3 Documents: folders over the existing table

- `documents.case_id` becomes nullable, so a passport belongs to the student and
  not to one application. Relaxing the constraint loses no data.
- Additions: `folder_id`, `expires_on`/`issued_on`, tags, colour, and a version
  group. The existing `superseded_by` chain becomes version history.
- Document types move from the pg enum to a per-tenant `document_types` table,
  seeded with today's 19 types. The enum column stays for compatibility.
- The status flow `Uploaded → Under review → Approved / Rejected → Re-upload
  requested` adds two enum values. `verified` is shown as "Approved".
- Folders are auto-created from per-tenant and per-country templates
  (Passport, Academic, Language Tests, Financial, Visa, Offer Letters, Other).
- Required-document sets are defined once here, and Module 2 stages reference
  them. That breaks the circular dependency between M1 checklists and M2
  stages.

### 3.4 Money: a double-entry core under today's invoices and payments

Today's invoice and payment rules stay: invoices are immutable, the ledger is
append-only, and "paid" is computed rather than stored. Underneath them the plan
adds a **double-entry journal** (`ledger_accounts`, `journal_entries`,
`journal_lines`). It is append-only through the same trigger technique as
`audit_log`, and corrections are made only with reversal entries. Invoices,
payments, refunds, expenses, commissions and payouts all post to it. Receivables,
the cash book, P&L, aging, period locks and reconciliation are all reports over
the journal, so they cannot disagree with each other. An automated check asserts
that the trial balance always sums to zero.

**This changes a documented rule.** The README says tuition and visa fees "never
pass through this ledger". The brief asks for application and visa fees and
"university fees paid on behalf of clients". The proposal treats these as
**disbursements**: they are invoiced and tracked, but posted to a pass-through
account that is excluded from revenue and profit. See decision D4.

### 3.5 Institutions: bring the catalogue back, in a smaller form

Commissions (M5) and the course finder (M8) both need a university master. The
catalogue removed in `0005` is not restored as it was. Phase 6 adds
`institutions` (profile, country, contacts, agreements, territories) plus
`programs` in Phase 10. `cases` gains an optional `institution_id` and keeps the
free-text fields, so nothing typed today is lost. See decision D3.

### 3.6 Leads are clients with a lifecycle

A client already exists from the first phone call. A separate `leads` table would
duplicate the person, the dedupe logic and the assignment logic. Instead,
`clients` gains `lifecycle` (lead / applicant / student / alumni), score,
temperature, campaign, source type (own / partner / referral) with a locked owner,
and a required **next action** with a due date while the client is active.

### 3.7 Platform services everything else depends on

- **Job queue in Postgres.** A `jobs` table with `FOR UPDATE SKIP LOCKED`,
  retries with backoff, dead-letter handling and a run log. No Redis is needed,
  and it works on PGlite. The scheduler runs on it, which also fixes the README's
  open item "the stuck sweep runs on every instance".
- **Mailer and messaging seams.** A `log` driver writes to `.data/outbox` in
  development. `smtp` handles email, and WhatsApp and SMS providers are added
  as credentials are supplied.
- **Branches** (from M13) are built into the foundations. Branch scoping has to
  live inside every `scope()`, so adding it after ten more modules would mean
  rewriting all of them.

## 4. Phases

Each phase finishes with the following before the next one starts:

1. API tests pass, and the new tables are included in the cross-tenant attack suite.
2. Every new permission's refusal is tested.
3. The page benchmark shows no unexplained query increase.
4. Migrations are tested forwards and backwards on a copy of the dev database.
5. The README and the compliance checklist are updated.
6. A short report shows what changed.

**Migration safety.** Every migration is additive, and a backfill runs inside the
same migration. Each migration ships with a hand-written down script in
`apps/api/drizzle/rollback/`. No column or table is dropped without asking you
first.

## 5. Risks

| Risk | Mitigation |
| --- | --- |
| **No version control** while rewriting the core | Phase 0 makes a baseline commit, and each phase is its own commit. |
| The stage engine rewrite (Phase 4) breaks auto-advance, analytics or the portal | A Standard template identical to today. Response snapshots diffed before and after. The enum column stays during the transition. |
| The auth hot path slows down (templates, branches, sessions) | All of it joins into the one existing `loadUser` query, and query counts are checked by the API benchmark. |
| Finance mistakes | Double-entry with a trigger that makes entries immutable. Reversal-only corrections. A trial-balance invariant tested on every run. Period locks enforced in SQL. |
| Scope creep and an unfinished half-state | Each phase ships usable on its own, and modules are behind plan or feature flags until complete. |
| PGlite is single-writer | The job worker runs in-process, and tests and benchmarks keep using throwaway databases. |
| Bundle growth (drag-and-drop, DOCX preview, charts) | Heavy libraries are lazy-loaded per screen, and first-load JS is tracked by the page benchmark. |
| `ALTER TYPE ... ADD VALUE` inside transactions | These go in their own migration statements with breakpoints, tested on PGlite and Postgres 16. |

## 6. What cannot be fully finished in this environment

These are built as **seams with a working local driver**. The real adapter is
written, and they are marked *Partial* until credentials or infrastructure
exist:

- WhatsApp Business API, SMS gateways, SendGrid/SES. SMTP works with any mailbox.
- Meta and Google lead ads. Stripe and PayPal (test mode with your keys).
- JazzCash and Easypaisa merchant APIs. QuickBooks and Xero APIs (file export works without them).
- Google and Microsoft calendar and Drive sync. SSO identity provider setup.
- Third-party e-signature: the in-app signature works without one.
- ClamAV daemon, Sentry, uptime monitoring, CDN.
- Docker: not installed here, so images are written but not built.
- CI runs and staging/production environments: these need a Git remote and a host.
- Native iOS and Android apps: the API stays ready for them, and the PWA ships.
